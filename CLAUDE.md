# CLAUDE.md — OFM (Orthodox File Manager)

You are building **OFM**, a keyboard-first, two-panel file manager for Ubuntu GNOME
(in the tradition of Norton Commander, Far Manager, Midnight Commander, Total/Double Commander).
Goal of this repository: ship **version 1.0.0** as defined in `docs/SPEC.md`.

Read these files before doing anything else in a new session:

1. `docs/PROGRESS.md` — where we are (source of truth for state; resume from here)
2. `docs/PLAN.md` — milestones, tasks, agent assignments, gates
3. `docs/SPEC.md` — what v1.0 must do (feature IDs F01–F33, theme spec)
4. `docs/ARCHITECTURE.md` — crates, core types, threading model, invariants
5. `docs/adr/` — architecture decisions already taken (do not silently reverse them)

## Your role in the main session: lead / orchestrator

- You plan, delegate, merge, verify, and keep `docs/PROGRESS.md` current.
- Implementation work goes to subagents defined in `.claude/agents/` (see "Agents" below).
  You write code yourself only for M0 bootstrap, small integration glue, and merge-conflict fixes.
- Keep your own context lean: ask agents for short reports (what changed, branch, test results,
  open issues), not for code dumps.
- Never spawn more than **4 implementation agents in parallel**. Parallel tasks must touch disjoint
  files/crates (the PLAN marks which tasks may run in parallel).

## Stack (decided — see ADR-0001)

- Rust (stable, edition 2024), Cargo workspace.
- UI: GTK 4 + libadwaita via `gtk4-rs` / `libadwaita-rs`, UI written in Rust code (no Blueprint, no Relm4).
- Terminal: VTE for GTK 4 (`vte4` crate).
- Minimum system libraries: GTK 4.14, libadwaita 1.5, VTE 0.76 (= Ubuntu 24.04 LTS); developed and
  tested on current Ubuntu (26.10). Do not enable crate features that require newer system libs
  without an ADR.
- No async runtime (no tokio) in v1.0. Core uses OS threads + channels (`async-channel`); the UI
  consumes events with `glib::spawn_future_local`.

## Workspace layout

```
crates/
  ofm-core/     # domain logic, NO gtk/glib/gio dependency, fully unit-testable
  ofm-vfs/      # Vfs trait + local fs + archive (read-only) + list (panelize) providers
  ofm-jobs/     # job engine + file operations (copy/move/delete/...) — data-safety critical
  ofm-config/   # config, keymap, themes (TOML), XDG paths
  ofm-viewer/   # viewer backend: mmap, line index, encodings, hex — no gtk
  ofm-search/   # find-files engine
  ofm-app/      # GTK 4 / libadwaita application (binary `ofm`)
  ofm-testkit/  # test helpers: fixture trees, tree comparison, fault plans (dev-dependency only)
tests/fixtures/ # generated by tests, never commit large binaries
docs/
```

## Hard invariants (a change that breaks one of these is a bug)

1. **No GTK/glib/gio types in any crate except `ofm-app`.** Core crates must compile and test headless.
2. **The GTK main thread never does file I/O.** No `std::fs`, no `read_dir`, no `stat` in `ofm-app`
   except via core APIs that run on worker threads. Exception: reading config at startup.
3. **No data loss.** File operations write to a temp name and rename into place; a failed or
   cancelled copy never leaves a truncated file under the final name and never deletes the source of a
   move before the destination is complete and synced. Every file-op change needs tests in `ofm-jobs`.
4. **Paths are bytes, not Strings.** Use `std::path::PathBuf`/`OsString`; never `to_str().unwrap()`.
   Non-UTF-8 file names must display (lossy) and work in every operation.
5. **Everything is a Command.** Every user action has a `CommandId`, is reachable by keyboard, and is
   rebindable via the keymap. No key handling hard-coded in widgets except text entry.
6. **No `unwrap()`/`expect()` in non-test code** except for invariants documented with a comment.
   Errors: `thiserror` in libraries, `anyhow` only in `ofm-app` main.
7. **No panics cross threads silently.** Worker panics are caught and reported as job errors.

## Commands

- Full check (must be green before every commit/merge): `./scripts/check.sh`
  (fmt check, clippy with `-D warnings`, all tests, UI smoke test under Xvfb)
- Fast loop for one crate: `cargo test -p <crate>`
- Run the app: `cargo run -p ofm-app`
- Screenshot of the running app for visual self-checks: `./scripts/screenshot.sh <name> [-- args]`
  (writes `target/screenshots/<name>.png`; open it with the Read tool to look at it)

## Git workflow

- Default branch `main`. One branch per task: `m<milestone>/<task-id>-<slug>`, e.g. `m3/T3.2-copy-engine`.
- Agents with `isolation: worktree` start from `main` — so **commit interface stubs to `main`
  before spawning agents that depend on them.**
- Conventional commits: `feat(jobs): ...`, `fix(app): ...`, `test(vfs): ...`, `docs: ...`.
  Reference task IDs in the body (`Task: T3.2`).
- Merge with `git merge --no-ff`, run `./scripts/check.sh` after every merge.
- Tag finished milestones: `m3-done`. Release tag: `v1.0.0`.

## Definition of done (per task)

- Acceptance criteria from `docs/PLAN.md` met; spec IDs referenced.
- Tests added (unit; plus integration for anything touching the file system).
- `./scripts/check.sh` green.
- Public items in core crates have doc comments.
- `docs/PROGRESS.md` updated by the lead (agents report, lead writes).

## Human gates

At gates G1, G2, G3, G4 (see `docs/PLAN.md`) **stop**. Write a short "please try this" checklist for
Igor into `docs/PROGRESS.md` and the chat, then wait for his feedback. Do not start the next milestone
before he answers. Also stop and ask if: a decision contradicts an ADR, a task fails twice after an
escalation, or something would require deleting user data outside `tests/` temp dirs.

## Agents (in `.claude/agents/`)

| Agent | Model / effort | Use for |
|---|---|---|
| `architect` | sonnet / high | Interfaces, trait stubs, ADRs, cross-crate design, untangling hard bugs |
| `core-engineer` | sonnet / high | ofm-core, ofm-vfs, ofm-config, ofm-viewer, ofm-search implementation |
| `fileops-engineer` | sonnet / high | ofm-jobs copy/move/delete engine (data-safety critical) |
| `ui-engineer` | sonnet / high | ofm-app GTK 4 / libadwaita UI |
| `test-engineer` | sonnet / medium | Test suites, fixtures, property tests, benchmarks, screenshots |
| `reviewer` | sonnet / high | Read-only review of merged milestone diffs against SPEC + invariants |
| `release-engineer` | sonnet / medium | Packaging (.deb, desktop file, AppStream), docs, release notes |

When delegating, always give the agent: task ID, spec IDs, the files/crates it owns, the files it
must not touch, acceptance criteria, and "report back: branch name, summary ≤ 15 lines, test results,
open questions".

## Budget policy (Igor is on a Pro plan: save Claude tokens)

- Everything runs on Sonnet. Opus only by explicit decision, e.g. one review of M3 (copy engine) at G2.
- Keep agent reports short; never re-read big docs in agents - give them only the relevant PLAN task and SPEC rows.
- **GLM offload (separate quota, via Z.ai Coding Plan):** `./scripts/glm.sh <worktree-dir> "<prompt>"` runs a headless
  Claude Code against the GLM endpoint. Offload disjoint, well-specified, non-GTK work:
  test-engineer tasks, release-engineer tasks, `ofm-viewer` (M5), `ofm-search` (M7), docs.
  Same rules apply (task ID, owned/forbidden files, acceptance criteria). The lead still merges and runs
  `./scripts/check.sh`; if GLM output fails check twice, redo the task with a Claude agent.
  Never offload: `ofm-jobs` (data safety), architect stubs, merges.

## Style

- `cargo fmt` default style; clippy clean with `-D warnings` (pedantic not required).
- Small modules; one responsibility per file; prefer plain structs + functions over trait objects
  except at the documented extension points (Vfs, JobKind, PreviewProvider).
- Log with `tracing` (`RUST_LOG=ofm=debug`). No `println!` outside tests and CLI output.
- User-facing strings in English for v1.0, wrapped in a single `tr()` helper so i18n (German, Russian)
  can be added later without touching call sites.
